# Golf WWG — Security & Project Review

**Date:** 2026-07-30
**Scope:** Full-project security review (database + application layers) and overall project health review, against `main` @ current (through migration 00030).
**Method:** Parallel specialist agents (database layer, application layer, project health), with the top security finding independently verified against source.

---

## Executive summary

The app is in solid beta shape — disciplined migrations, current architecture docs, consistent server-action patterns — but the review surfaced **one critical, trivially-exploitable privilege-escalation vulnerability**, a cluster of authorization-scope gaps (14 security findings total: 1 critical, 4 high, 5 medium, 4 low), and several structural issues (a dead backend layer, divergent generated types, a non-transactional destructive write, and near-zero automated test coverage).

**Fix first, today:** any registered user can make themselves site admin and then delete any user or group in the system (Finding S1). This is a one-request exploit and should be patched before anything else. Close behind: three high-severity authorization omissions in server actions (S2 share-code over-grant, S8 season IDOR, S9 fabricated settlements).

Security findings are split into **database-layer** (S1–S7) and **application-layer** (S8–S14).

## Security findings

Severity + confidence (1–10) shown per finding. Database-layer findings verified by the DB review agent; **S1 additionally verified by hand against source.**

### S1 — Any user can self-escalate to site admin → delete any user/group  🔴 CRITICAL
- **Location:** `supabase/migrations/00001_initial_schema.sql:24-26` (policy) + `supabase/migrations/00012_site_admin.sql:8-9` (column) + `apps/web/src/lib/actions/admin.ts`
- **Severity:** HIGH / Critical · **Confidence:** 9 (verified)
- **Category:** Privilege escalation (missing `WITH CHECK` on writable privileged column)
- **Description:** The `profiles` UPDATE policy is `USING (auth.uid() = id)` with **no `WITH CHECK` clause**, and it is never redefined in any later migration. Migration 00012 added `is_site_admin BOOLEAN` to that same row. A user can therefore set their own `is_site_admin = true`. Server-side, `is_site_admin` gates `admin.ts`, whose actions run through the **service-role client**: `adminDeleteUser` (deletes any auth user), `adminDeleteGroup` (deletes any group), `adminSoftDeleteCourse`, `adminDeleteInvitation`.
- **Exploit:** Authenticated user Alice sends a normal PostgREST PATCH to her own profile row: `UPDATE profiles SET is_site_admin = true WHERE id = <her id>`. Policy passes (`auth.uid() = id`). Alice reloads the app as a site admin and can now delete any user account and any group in the system.
- **Fix:** Add a `WITH CHECK` to the `profiles` UPDATE policy that forbids changing `is_site_admin` (compare to the existing value via a `SECURITY DEFINER` helper), **or** move `is_site_admin` to a separate table with deny-all RLS mutated only by the service role. Also consider protecting `current_handicap_index` (self-writable today → handicap manipulation).

### S2 — Share-code join grants permanent, full parent-group access  🟠 HIGH
- **Location:** `supabase/migrations/00026_share_code.sql:74-133` (`join_round_by_code`), esp. lines 97-99
- **Severity:** HIGH · **Confidence:** 8
- **Category:** Over-broad grant via `SECURITY DEFINER` share-code flow
- **Description:** Redeeming a 6-char code inserts the caller as a **permanent `member`** of the round's parent group. That unlocks all group-gated RLS — every co-member's profile, every round, every score, every game, and all `settlements` (financial) data — not just the shared round, and it never expires.
- **Exploit:** Bob obtains one valid share code (shoulder-surf, forwarded screenshot), calls `join_round_by_code('ABCD12')`, and gains permanent read access to the entire group's members, history, scores, and payouts.
- **Fix:** Don't grant parent-group membership for a code join. Use a round-scoped participant association (e.g. a `round_guests` row) with narrow RLS, or auto-evict share-join memberships when the round finalizes.

### S3 — `send-round-notification` has no authorization scoping  🟠 MEDIUM (HIGH if invitation IDs leak)
- **Location:** `supabase/functions/send-round-notification/index.ts:26-66`
- **Severity:** MEDIUM · **Confidence:** 8
- **Category:** Missing authorization check in edge function
- **Description:** Only verifies the caller is *some* authenticated user, then uses the **service role** to load a round by `roundId` and invitations by attacker-supplied `invitationIds`, with no check that the caller owns/admins the round or that the invitations belong to it. Sends real emails containing live RSVP tokens. (Contrast `send-invitation`, which checks admin role.)
- **Exploit:** Any authenticated user posts a `roundId` + arbitrary `invitationIds`; the service role emails RSVP links to those addresses without any membership gate.
- **Fix:** Mirror `send-invitation` — verify caller is round creator or group admin for `round.group_id`, and constrain the query with `.eq('round_id', roundId)`.

### S4 — Shared-mode score policy allows overwriting any player's card  🟡 MEDIUM
- **Location:** `supabase/migrations/00024_scorecard_confirmation.sql:222-274`
- **Severity:** MEDIUM · **Confidence:** 7
- **Category:** Overly permissive write / cross-player tampering
- **Description:** In default `shared` scoring mode, INSERT/UPDATE `scores` policies grant write to *any* round_player, with no restriction on which `player_id` is written and no `WITH CHECK` on UPDATE. Any participant can alter any other's strokes, which feed handicap differentials and payouts.
- **Fix:** Restrict shared-mode writes to `scores.player_id = auth.uid()`; route cross-player entry only through the scorekeeper/flight-scorer branches. At minimum add a `WITH CHECK` to the UPDATE policy. *(Partly intended for casual scoring — decide product intent.)*

### S5 — `claim_scorer` lets any participant seize scoring control  🟡 MEDIUM
- **Location:** `supabase/migrations/00030_self_service_scorer.sql:19-42`
- **Severity:** MEDIUM · **Confidence:** 7
- **Category:** `SECURITY DEFINER` authorization too weak
- **Description:** Only checks a `round_player` row exists for `(round_id, auth.uid())`. In a whole-round shared round it sets `scorekeeper_id = caller` and flips `scoring_mode` to `'scorekeeper'`, locking all other players out of entering their own scores. Combined with S2, an outsider who joined by code can hijack scoring.
- **Fix:** Gate self-service scorer behind an explicit per-round opt-in (default off) or creator/admin approval; don't let an arbitrary participant flip round-wide `scoring_mode`.

### S6 — Memberless-group INSERT policy allows arbitrary self-add as admin  🟢 LOW
- **Location:** `supabase/migrations/00005_fix_rls_recursion_v2.sql:41-48`
- **Severity:** LOW · **Confidence:** 6
- **Category:** Overly permissive INSERT / potential group takeover
- **Description:** `group_members` INSERT passes if caller is group admin **or** the group has no members. The first-member branch doesn't restrict `user_id = auth.uid()` or `role`, so any group that reaches zero members can be claimed by anyone as `admin`.
- **Fix:** Constrain the first-member branch to `user_id = auth.uid()` and combine with a `created_by = auth.uid()` check on the group.

### S7 — `calculate-handicap` writes a record for an unvalidated roundId  🟢 LOW
- **Location:** `supabase/functions/calculate-handicap/index.ts:49-169`
- **Severity:** LOW · **Confidence:** 6
- **Category:** Weak input validation (self-affecting only)
- **Description:** Verifies caller identity and round participation, but stamps the computed `handicap_records` row with a caller-supplied `roundId` that isn't validated to correspond to the computation. Impact limited to the caller's own record.
- **Fix:** Validate `roundId` is a completed round the user played before writing, or derive it server-side.

### App-layer findings

#### S8 — `updateSeason` / `deleteSeason` skip the admin check → cross-group IDOR  🟠 HIGH
- **Location:** `apps/web/src/lib/actions/seasons.ts:55-103`
- **Severity:** HIGH · **Confidence:** 9
- **Category:** Missing authorization check (IDOR)
- **Description:** Both authenticate via `getUser()` but perform **no** authorization check — they fire `.eq('id', seasonId)` and rely entirely on RLS. The sibling `createSeason` correctly requires `membership.role === 'admin'`, so the omission is clearly a bug.
- **Exploit:** A member of any group calls `updateSeason(otherGroupsSeasonId, ...)` or `deleteSeason(otherGroupsSeasonId)` with a season UUID from a group they don't administer. If the `seasons` RLS isn't strictly admin-scoped, they overwrite/destroy another group's season.
- **Fix:** Fetch the season's `group_id` and require caller `role='admin'` there, mirroring `createSeason`.

#### S9 — `createSettlements` lets any user fabricate financial records  🟠 HIGH
- **Location:** `apps/web/src/lib/actions/settlements.ts:5-27`
- **Severity:** HIGH · **Confidence:** 8
- **Category:** Missing authorization check
- **Description:** Verifies authentication but not authorization on `roundId` or the `payerId`/`payeeId` values. Any authenticated user who knows a round UUID can insert arbitrary settlement rows naming any players.
- **Exploit:** Attacker calls `createSettlements(victimRoundId, [{ payerId: victimUserId, payeeId: attackerUserId, amount: 1000 }])`, fabricating a debt that shows up in the victim's settlements view.
- **Fix:** Require caller to be round creator (Commish) or group admin before inserting — reuse the `round.created_by === user.id` / group-admin pattern from `finalizeGame`.

#### S10 — PostgREST `.or()` filter-string injection via unvalidated `playerId`  🟡 MEDIUM
- **Location:** `apps/web/src/lib/actions/scores.ts:39`, `apps/web/src/lib/actions/tee-time-groups.ts:80`
- **Severity:** MEDIUM · **Confidence:** 7
- **Category:** Filter-string injection (not SQL injection — pg values stay parameterized)
- **Description:** Both build `.or(\`user_id.eq.${playerId},id.eq.${playerId}\`)` by raw-interpolating a caller-supplied `playerId`. A crafted value can inject extra filter clauses and broaden the predicate beyond the intended single player.
- **Exploit:** In `scores.ts`, a participant supplies `playerId = "x),or(1.eq.1"`; the predicate may expand to match rows beyond their own, resolving a different player's row. (In `tee-time-groups.ts` the caller is already a verified admin, lowering severity.)
- **Fix:** Validate `playerId` as a UUID before interpolation, or replace `.or()` with two explicit `.eq()` queries / an `.in()` lookup.

#### S11 — `declineRoundInvite` misses invite-email ownership check  🟡 MEDIUM
- **Location:** `apps/web/src/lib/actions/rounds.ts:1082-1110`
- **Severity:** MEDIUM · **Confidence:** 7
- **Category:** Missing ownership verification
- **Description:** Validates the token is pending/unexpired but — unlike `acceptRoundInvite` (line 897) — doesn't verify the caller's email matches `invitation.email`. Anyone with another user's invite token can decline it.
- **Exploit:** User A obtains User B's round invite token (forwarded link), calls `declineRoundInvite(tokenB)`, and removes User B from the round without consent.
- **Fix:** Add the email-match guard used by `acceptRoundInvite` before updating status.

#### S12 — Exported service-role push helper is a standing trust-boundary hazard  🟡 MEDIUM
- **Location:** `apps/web/src/lib/push.ts:32` (`sendPushToUsers`)
- **Severity:** MEDIUM · **Confidence:** 6
- **Category:** Service-role client bypasses RLS
- **Description:** Uses `createServiceRoleClient()` to read sensitive push subscription material (`endpoint`, `p256dh`, `auth`) filtered only by `in('user_id', userIds)`. Current callers pass server-derived IDs, but the function is **exported** — any future caller passing arbitrary user IDs reads arbitrary subscription secrets with no authz boundary.
- **Fix:** Make it module-private, or use the RLS client where possible; never let user input drive `userIds`.

#### S13 — `getCourseTeeBoxes` is an unauthenticated server action  🟢 LOW
- **Location:** `apps/web/src/lib/actions/courses.ts:354-367`
- **Severity:** LOW · **Confidence:** 6
- **Description:** This `'use server'` action fetches tee-box data for any `courseId` with no `getUser()` check (unlike sibling `getRecentCourses`). Server actions are POST-invokable, so it's an unauthenticated (low-sensitivity) data-read path.
- **Fix:** Add the `getUser()` guard used by `getRecentCourses`.

#### S14 — Middleware route protection uses a fragile allowlist  🟢 LOW
- **Location:** `apps/web/src/lib/supabase/middleware.ts:38-44` + `apps/web/middleware.ts:9-12`
- **Severity:** LOW · **Confidence:** 6
- **Description:** Protection is an explicit prefix allowlist (`/home`, `/groups`, `/rounds`, `/courses`, `/profile`, `/settings`, `/admin`). Any protected page outside that list (e.g. `/play`, `/scorecard`, `/seasons`, future routes) isn't redirected for unauthenticated users — enforcement falls back to server actions + RLS. (`getUser()` is used correctly, not `getSession()`.)
- **Fix:** Invert to a public-route blocklist so new routes are protected by default.

#### App-layer posture (summary)
Generally solid: every mutating action establishes identity with `getUser()` (never the spoofable `getSession()`), the anon client is used throughout so RLS stays the backstop, and the service-role client is confined to `admin.ts` (site-admin gated), `groups.ts` `deleteUser` (gated), and `push.ts` (server-derived IDs). Round/group/game mutations consistently re-check `created_by`/admin role server-side. **No secret leakage** — no service-role or VAPID private key reaches any `'use client'` file. The gaps are authorization omissions in a few actions (S8, S9, S11) plus two broader-than-intended read paths (S13, S14) and the `.or()` interpolation (S10). *(Note: the edge-function layer S3/S7 lives in dead code — see P1 — but the functions remain deployed and invocable.)*

### Database security posture (summary)
Structurally sound and clearly iterated: RLS enabled on every application table, consistent group-membership gating across rounds/scores/games/settlements, RLS-recursion resolved via pinned-`search_path` `SECURITY DEFINER` helpers, and earlier over-permissive policies deliberately tightened in 00003. All `SECURITY DEFINER` functions pin `search_path = public`, qualify names, and bind parameters (no SQL injection; `gen_share_code` uses a fixed alphabet). Edge functions correctly separate a user-JWT client (authz) from a service-role client (privileged work), and email templates escape input. The material weaknesses are **authorization-scope gaps, not disabled RLS** — chiefly S1, S2, and S3.

## Project health review

### What's working
- **Migration discipline** and `docs/architecture.md` (dated 2026-07-27, "through 00030") are genuinely current — a model doc.
- `packages/core/src/validation` (24 Zod schemas) is a real contract layer used by most server actions; the game engine (12 formats) is consumed via `packages/ui` hooks → `games-view.tsx`.
- Server actions follow a consistent `{ error }` return contract.

### P1 — Dead backend layer + triplicated money math
None of the five `supabase/functions/*` edge functions is invoked anywhere (`finalize-round` → superseded by the `finalize_round` RPC; `send-invitation` → superseded by `lib/email.ts`; `calculate-handicap`/`calculate-payouts` → nothing). Consequence: **`handicap_records` has no writer** (the handicap page reads a table nothing populates), and WHS handicap math exists in **three divergent copies** (core `handicap/index-calc.ts`, the edge fn, and a display copy in the handicap page). Course-handicap formula is inlined in 6 files; `strokesReceivedOnHole` in 3.

### P2 — Divergent generated DB types + 128 `as any` casts
`apps/web/src/lib/supabase/database.types.ts` is current, but `packages/core/src/types/database.generated.ts` is ~8 tables stale and re-exported from `@golf/core`, so **two divergent `Database` types coexist**. 128 `as any` casts (31 in the round page alone) paper over untyped Supabase relations.

### P3 — Correctness bug: guest scores dropped from leaderboard
`apps/web/src/app/(dashboard)/rounds/[roundId]/page.tsx:278` filters the leaderboard on `p.user_id && playerScores.has(p.user_id)`, but the score map is keyed `player_id ?? round_player_id` to include guests — so **guest scores are aggregated then silently excluded** from the leaderboard.

### P4 — Non-transactional destructive write
`saveTeeTimeGroups` (`lib/actions/tee-time-groups.ts`) deletes all existing groups and clears `round_players.tee_time_group_id` **with no error checks and no transaction**, then rebuilds via N+1 loops. A mid-loop failure leaves the round's foursomes wiped. Also builds a PostgREST `.or()` filter by string interpolation. Should be a single `SECURITY DEFINER` RPC.

### P5 — Near-zero test coverage
Total test surface: 2 Playwright smoke tests (untracked, not in CI). CI runs type-check + build only. The highest-value, cheapest gap: `packages/core` (12 game-format engines + WHS math) is pure, dependency-free logic with **zero unit tests** — and payouts/handicaps are exactly what users will argue about.

### Smaller items
- `CLAUDE.md` is stale (omits 8 tables added since 00009; documents the dead edge functions as active).
- `packages/ui` contains no components (only 3 hooks) — misnamed; UI primitives live in `apps/web`.
- Feature flags (6, build-time `NEXT_PUBLIC_*`) are well-documented but `playExperience`/`navV2` off-paths are now permanent dead weight.
- `revalidatePath` used zero times; freshness relies on scattered `router.refresh()`.
- Repo hygiene: root junk files (`nul`, screenshots, `ts-errors*.txt`, `tsconfig.tsbuildinfo`) need `.gitignore` entries. *(cleaned from working tree 2026-07-30)*
